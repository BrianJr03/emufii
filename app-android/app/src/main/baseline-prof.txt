# Ahead-of-time compilation profile.
#
# What it is, and why it exists. Android does not install a compiled
# application: ART interprets it, then compiles on the fly what it sees coming
# back often, and only compiles seriously after several hours, in the
# background, once the device is at rest. The first sessions therefore run
# interpreted, precisely the ones on which the app's smoothness is judged.
#
# This file tells ART what to compile from installation onwards. It is packaged
# in the APK under `assets/dexopt/`, and `androidx.profileinstaller` hands it to
# the system on first launch.
#
# Measured on the Thor, 25 fast scrolls down the grid, on 2026-08-29.
# Same code, same device, only the compilation changes:
#
#   | build                     | median | 90th  | 99th  | late  |
#   |---------------------------|--------|-------|-------|-------|
#   | debug (interpreted)       |  12 ms | 48 ms | 113 ms|  16 % |
#   | release, not compiled     |   9 ms | 53 ms |  97 ms|  21 % |
#   | release, compiled         |   9 ms | 31 ms |  46 ms|  16 % |
#
# It is the tail that moves, and the tail is what you feel: the isolated 100 ms
# hitches drop by half. A *debug* build cannot be compiled at all: ART refuses
# to optimise debuggable code, so judging smoothness on a debug build means
# nothing, and that is what we were doing.
#
# Cocoon, the launcher next door, ships one (`assets/dexopt/baseline.prof`) and
# runs in `speed-profile`: 5 ms median, 6 ms at the 90th, no late frames. That
# is where the lead came from.
#
# This profile is written by hand, with wildcards. The official tool
# requires a macrobenchmark module that replays a journey on the device; here we
# list the packages known to be on the hot path: the library, its cursor, the
# plastic material, the background, the second screen. It does not have to be
# exhaustive: what it misses is simply compiled later, as before.
#
# `H` = hot (called often), `S` = at startup, `P` = to be compiled.
